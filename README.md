# Three-Way Match Engine for PO, GRN, and Invoice

A Node.js & Express backend service that automates the matching of Purchase Orders (PO), Goods Receipt Notes (GRN), and Invoices using the Gemini API for document parsing and MongoDB for persistence.

## Approach & Architecture

The backend consists of:
1. **Express Server (`index.js`)**: Entry point of the application setting up middleware and routes.
2. **MongoDB Connection (`config/db.js`)**: Manages the connection to a MongoDB database.
3. **Mongoose Model (`models/Document.js`)**: A single unified document collection to store raw parsed JSON data from all three types of documents independently.
4. **Gemini Parsing Service (`services/geminiServices.js`)**: Leverages the Gemini API with structured schema instructions (`responseMimeType: "application/json"`) to convert uploaded document streams (PDFs/images) into clean, type-safe JSON objects.
5. **Matching Engine (`services/matchService.js`)**: Implements item-level validations and checks out-of-order document relations dynamically when requested.

---

## Data Model

Documents are stored in a single Mongoose collection named `Document` with the following structure:

```json
{
  "_id": "ObjectId",
  "docType": "PO | GRN | INVOICE",
  "poNumber": "string",
  "originalFileName": "string",
  "parsedData": "Mixed (dynamic JSON object containing the parsed document fields)",
  "createdAt": "Date"
}
```

---

## Parsing Flow

1. The client uploads a document via `POST /documents/upload` with form-data (`file` and `docType`).
2. The file buffer is sent directly to `gemini-2.5-flash` model along with a structural system prompt dictating the exact JSON output format.
3. Gemini processes the document and returns a structured JSON string.
4. The system parses the JSON, extracts the `poNumber`, and persists the document record in MongoDB.

---

## Matching Logic & Choice of Key

### Matching Key
The engine performs matching at the **item level** using standardizing logic:
*   **Key Choice**: `item.itemCode || item.sku || item.description || 'unknown'`
*   **Rationale**: Different systems structure items differently; some use internal codes (`itemCode`), some barcodes/SKUs (`sku`), and others fall back to clean item descriptions. By normalizing this key (lowercase, trimmed space), we ensure maximum reliability across documents generated by different suppliers.

### Validations & Statuses
The engine runs item-level and date validations:
1. **GRN quantity <= PO quantity**: Ensures the vendor did not deliver more than ordered.
2. **Invoice quantity <= Total GRN quantity**: Ensures we are not billed for more than we received.
3. **Invoice quantity <= PO quantity**: Ensures invoice is bounded by order size.
4. **Invoice date <= PO date**: Ensures invoices are not backdated before the purchase order.

**Possible Match Output Statuses**:
*   `matched`: All documents are present, quantities match perfectly, and dates are valid.
*   `partially_matched`: Missing some quantities or items, but no rules are violated.
*   `mismatch`: Validation rules were violated (e.g., invoice quantity exceeds GRN quantity, or invoice date is prior to PO).
*   `insufficient_documents`: Missing a PO, or missing a GRN/Invoice entirely.

---

## Out-of-Order Upload Handling

Because documents can arrive in any order (e.g., Invoice uploaded before PO), the system:
1. Saves each parsed document independently without blocking.
2. Calculates the relationship dynamically using the `poNumber` index on the fly.
3. Allows querying `GET /match/:poNumber` at any point to retrieve the latest state of matching, resolving matching state dynamically regardless of arrival order.

---

## Assumptions & Tradeoffs

### Assumptions
*   A single Purchase Order is the source of truth; multiple POs with the same `poNumber` are treated as a mismatch (`duplicate_po`).
*   Dates returned by Gemini are parsed using JS `Date` and are comparable.
*   A PO is required to perform matching. If no PO is present for a given `poNumber`, it returns `insufficient_documents` with reason `missing_po`.

### Tradeoffs
*   **On-the-fly Calculation vs. Persistent State**: Computing matches on `GET` is highly flexible, but can be slow if there are thousands of items. Persisting state in MongoDB would speed up reads but add writing/concurrency complexity. Given the current requirements, on-the-fly logic provides a cleaner, simpler implementation.

---

## Future Improvements
- **Asynchronous / Queue-Based Processing**: Offload slow Gemini API document parsing to a background worker queue (e.g. BullMQ, RabbitMQ) to make file uploads near-instantaneous.
- **Fuzzy Matching for Items**: Implement Levenshtein Distance or semantic vector embeddings to match item descriptions when exact `itemCode` or keys do not line up perfectly across documents.
- **Persistent Match Cache**: Cache calculated match outcomes in MongoDB and only recalculate/invalidate them when a new document under that `poNumber` is uploaded.

## Getting Started

### Prerequisites
- Node.js (v18+)
- MongoDB running locally or a MongoDB Atlas connection string.
- Gemini API Key.

### Installation & Run

1. **Clone the repository** and navigate to the project directory.
2. **Install dependencies**:
   ```bash
   npm install
   ```
3. **Configure environment variables**:
   Create a `.env` file in the root directory:
   ```env
   PORT=3000
   MONGODB_URI=mongodb://localhost:27017/match_engine
   GEMINI_API_KEY=your_gemini_api_key_here
   ```
4. **Start the application**:
   ```bash
   npm run dev
   ```
   The server will start on port `3000` (or the port specified in your `.env` file).
